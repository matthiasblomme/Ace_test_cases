# XmlnscForLoop - does `FOR o AS path.Order[]` walk XMLNSC repeating elements correctly?

One Compute walks the repeating `Order` children of `Orders` in several ways and returns, per
method, the iteration count and the `id` values seen, in order, as JSON:

- FOR: `FOR o AS InputRoot.XMLNSC.Orders.Order[] DO ... END FOR;`
- WHILE REPEAT TYPE NAME: `DECLARE r REFERENCE TO ...Order[1]; WHILE LASTMOVE(r) DO ... MOVE r NEXTSIBLING REPEAT TYPE NAME; END WHILE;`
- WHILE NAME: the same walk with `MOVE r NEXTSIBLING NAME 'Order'` (the form the ACE Flow Pilot
  ESQL guidelines recommend instead of FOR)
- WHILE NAMESPACE NAME (`?ns=1` only): `MOVE r NEXTSIBLING NAMESPACE ns NAME 'Order'`

`?ns=1` switches every path to `InputRoot.XMLNSC.ns:Orders.ns:Order` with
`DECLARE ns NAMESPACE 'urn:example:orders'`. The response also lists every child of `Orders`,
unfiltered, as `FIELDNAME:FIELDTYPE`, so you can see what the parser built. `ForLoopFlow`
(`/forloop`) uses default XMLNSC parser options. `ForLoopMixedFlow` (`/forloopmixed`) is
identical, except that it sets `parserXmlnscMixedContentRetainMode="all"` on the HTTPInput. That
attribute name and its values (`none`, `all`) come from
`common/schemas/MessageFlow/MessageFlow.xsd` in the 13.0.9.0 install, where
`ComIbmWSInputNodeType` includes `parserXmlnscAttributes`. Both flows share one ESQL module.

Run on 2026-11-03, ACE 13.0.9.0 (Windows), stand-alone integration server.

## Run

Same steps as `HttpReplyStatusCode/TESTING.md`, with `--project XmlnscForLoop`, then
`curl -i -X POST -H "Content-Type: application/xml" --data-binary @test-messages/<file> "http://localhost:<port>/forloop"`.
Add `?ns=1` for C1 and C2. Use `/forloopmixed` for H. `G_thousand_orders.xml` was generated by a
script: 1000 `<Order><id>n</id></Order>` siblings, with n = 1..1000.

## What this shows

- FOR visited every Order, in document order, in every case, with no exception. That includes
  interleaved other elements, both namespace forms, a foreign-namespace Order, pretty-printed
  input, retained mixed content, and 0, 1 and 1000 items. On 13.0.9.0, the claim that the FOR form
  "does not correctly traverse sibling nodes in the XMLNSC domain" did not reproduce.
- The form recommended in place of FOR, `MOVE r NEXTSIBLING NAME 'Order'`, is the one that broke.
  Without a NAMESPACE clause, NAME matches only the empty namespace, which is the documented
  "Name in the default namespace" row of the MOVE statement. On a namespaced document it stops
  after the first Order (C1). It can also jump to a no-namespace `Order` and stop there (C2). Adding
  `NAMESPACE ns` to the MOVE fixes both cases.
- `REPEAT TYPE NAME` also matches on field type, so a leaf `<Order>2</Order>` between folder
  Orders is skipped (X2). FOR and `NAME` do not filter on type.
- Retaining mixed content does put whitespace siblings between the Orders (H). All the walks skip
  them, because each one filters on name. The unqualified `MOVE c NEXTSIBLING` walk behind the
  child listing does land on them.
- Not covered: trees built in ESQL (OutputRoot, Environment), loops that modify the tree they
  walk, and other parsers.
